## Why

`docs/TITLE_PATH.md` (L35): window creation calls 0x01106C80
unconditionally, and it uses IMM32: ImmGetDefaultIMEWnd, ImmGetContext,
ImmSetCompositionWindow, ImmSetCandidateWindow, ImmReleaseContext and
ImmSetOpenStatus. The game imports more:
- ImmGetOpenStatus;
- ImmGetCompositionStringA/W;
- ImmGetCandidateListCountA, ImmGetCandidateListW;
- ImmGetVirtualKey.
claude-2's boot will reach them right after the window. claude-2 is busy
on the boot itself, so this moves to you.

The IME object is `DAT_018D4018`. 0x00DF1200 allocates it (0x1018 bytes)
and constructs it with 0x01106610.

The text entry is character and pawn naming:
- uGUICharacterEdit1;
- cNameEditor;
- the keyboard interface, whose Steam Big Picture branch is L26's
  ShowGamepadTextInput.

With no IME open, all of it sees "closed, nothing composed": typed
characters arrive as WM_CHAR.

### 2. Measured answers and implementation

The probe ran on Windows 11 26200 in a **32-bit** process. It used a
window made like the game's (style 0x00CA0000, before ShowWindow) and the
game's arguments, then repeated every call with a NULL context. Every
answer below is in `tests/imm32.rs`.

| Call | With the default context | NULL context |
|---|---|---|
| ImmGetDefaultIMEWnd | the thread's IME window (class "IME", hidden, owned by the first top-level window), also for NULL; NULL before any top-level window | |
| ImmGetContext | the same non-NULL context each time | NULL for a NULL window |
| ImmReleaseContext | TRUE (also twice, also NULL) | TRUE |
| ImmSetCompositionWindow / ImmSetCandidateWindow | TRUE (read back unchanged) | FALSE, ERROR_INVALID_HANDLE |
| ImmSetOpenStatus(FALSE) / ImmGetOpenStatus | TRUE / FALSE | FALSE + error 6 / FALSE, no error |
| ImmGetCompositionStringA/W (8, 0x10, 0x800; with a buffer or NULL/0) | 0, buffer untouched | 0 |
| ImmGetCandidateListCountA | **144**, `*count` = 0 | 0, `*count` = 0 |
| ImmGetCandidateListW (buffer or NULL) | 0, untouched | 0 |
| ImmGetVirtualKey | 0xE5 (VK_PROCESSKEY): no message, after a WM_KEYDOWN, with or without TranslateMessage, also for NULL | |

Further measured answers, from a second probe run and confirmed by
claude-2's own probe on task/L21-boot:
- **Last error:** a successful Set*Window, SetOpenStatus or GetOpenStatus
  sets it to 0. GetContext and ReleaseContext leave it alone.
- **A handle that is no window:** GetContext and GetDefaultIMEWnd answer
  NULL with ERROR_INVALID_WINDOW_HANDLE (1400). GetVirtualKey answers 0xE5,
  also with 1400 (input.rs does not set that error; noted, not changed).
- **Notifications** go to the window that has the context once it is shown
  and focused, and none are sent before ShowWindow, which is when
  0x01106C80 runs:
  - SetCompositionWindow sends WM_IME_NOTIFY(IMN_SETCOMPOSITIONWINDOW 0xB);
  - SetCandidateWindow sends IMN_SETCANDIDATEPOS(9, 1 << dwIndex);
  - SetOpenStatus sends IMN_SETOPENSTATUS(8), only on a change;
  - opening is kept and read back.
- **Activation:** it sends WM_IME_SETCONTEXT(TRUE, ISC_SHOWUIALL
  0xC000000F), then WM_IME_NOTIFY(IMN_OPENSTATUSWINDOW 2), between
  WM_ACTIVATE and WM_SETFOCUS. user32's activate() now sends both. The
  game's handlers (0x011066D0, 0x011066E0) keep no state from them.

How the runtime models it:
- The default IME window is a handle the desktop creates with the first
  top-level window. It has no window record, and the game sends it
  nothing (**runtime choice**, labelled).
- The context is one fixed handle.
- The forms and the open status are kept.
- `ImmGetVirtualKey` already answered 0xE5 in `input.rs`. The probe
  confirms that value, so it stays there.
- Not measured, labelled in the code:
  - a candidate index above 3;
  - a handle that is no window.

The 144 is this Windows build's answer for an empty list. The game only
reads the count from it.

### 4. The byte 0x018D0158

It is **MtRegistry's "config.ini did not exist" flag**: 0x018CFF48 +
0x210. MtRegistry's constructor 0x00CFFF00 sets it when
GetFileAttributesW on the config.ini path fails.

There is no direct writer, because the code addresses it as +0x210 of
the registry object; a byte scan of .text for 0x018D0140..0x018D016F
finds only the read at 0x0041CE9A.

So the start-up writes the options menu only on a **first run**. That is
why a new config.ini begins with the menu's keys in the menu's order.
L34's OPTIONS.md and Results now say so (task/L34-options 8db9a66).
